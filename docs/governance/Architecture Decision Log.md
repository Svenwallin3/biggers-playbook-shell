**ADL-001**
Date: 2026-08-01 (locked pre-build)
Decision: Frontend on Lovable, backend on native/BYO Supabase (not Lovable's managed Cloud backend).
Reason: Reason not documented beyond general platform choice; BYO Supabase was later confirmed necessary to allow Claude's Supabase MCP direct access alongside Lovable's.
Affected areas: entire stack.
Alternatives rejected: Lovable Cloud (managed backend) — was in fact accidentally triggered once via a mislabeled "Use Supabase" button and reversed.
Status: Active.

**ADL-002**
Date: 2026-08-01
Decision: No Homebase sync for employee provisioning. Employees self-register with name + email; passwordless magic-link auth for all staff.
Reason: Avoids weekly CSV export/upkeep; a mistyped email fails visibly at signup with a trainer present rather than creating a silent orphan account weeks later.
Affected areas: auth, employee lifecycle, onboarding flow.
Alternatives rejected: Homebase CSV sync with auto-deactivation/auto-role-routing.
Status: Active.

**ADL-003**
Date: 2026-08-01
Decision: `content_status` (ready/needs_restructuring/missing/blocked) as a placeholder mechanism, enabling structure-first build with content backfilled visibly rather than gated on every piece being finished.
Reason: Lets Sven see the shape of the app and gather content against a concrete visual; avoids one giant content-complete launch.
Affected areas: modules, steps, reference_documents; `/admin/gaps` dashboard.
Alternatives rejected: build only after all content is ready.
Status: Active.

**ADL-004**
Date: 2026-08-01 → 2026-08-03
Decision: Staged Lovable build (scaffold → UI on mock data → Supabase schema/auth → wire to live data → polish), checkpointed between stages, never one uninstructed mega-prompt.
Reason: Lovable's own stated guidance that single giant prompts for complex apps underperform, and connecting backend too early makes early iteration harder to debug.
Affected areas: entire build process.
Alternatives rejected: single comprehensive build prompt.
Status: Active (governs future Lovable work too — see [[feedback_lovable_build_process]]).

**ADL-005**
Date: 2026-08-01
Decision: No hard deletes, ever, on content tables — soft-delete (`is_deleted`/`deleted_by`/`deleted_at`) plus append-only `version_history` with full restore capability.
Reason: Prevents a disgruntled or exiting manager from destroying content; preserves an audit trail.
Affected areas: modules, steps, tracks, reference_documents, presentation_reference_entries, sourcing_board_entries.
Alternatives rejected: standard hard-delete with confirmation dialog.
Status: Active, with two approved exceptions — see ADL-011 (`merge_employees()` duplicate rows) and ADL-090 (`manager_notes`, 30 days after soft-delete).

**ADL-006**
Date: 2026-08-01
Decision: Every module/step/reference document carries a `location_tag` field from day one, even though multi-location content isn't being authored yet.
Reason: Avoids a later schema fork when multi-location content becomes real; tag individual records rather than forking whole tracks per location.
Affected areas: tracks, modules, steps, reference_documents.
Alternatives rejected: fork entire tracks per location when the need arises.
Status: Active.

**ADL-007**
